# 4) MODULE — WORKFLOW DE VALIDATION

## Objectif
Certaines actions sensibles ne doivent plus être définitives immédiatement.
Je veux un workflow de validation configurable.

## Cas métier à couvrir
Le système doit permettre, selon paramétrage :
- validation d’une opération au-delà d’un certain montant
- validation d’un transfert inter-caisses
- validation d’un dépôt banque
- validation d’une clôture avec écart
- validation d’une annulation d’opération
- validation d’une réouverture éventuelle de session si tu prévois ce cas

## Entités à créer
- ApprovalRule
- ApprovalRequest
- ApprovalAction

## Enums attendus
- ApprovalTargetType
- ApprovalStatus
- ApprovalActionType si utile

## Exemples de règles
- toute sortie > 100000 nécessite validation
- tout transfert nécessite validation
- tout dépôt banque nécessite validation
- tout écart > seuil nécessite justification et validation

## Règles métier attendues
- si une action nécessite validation, elle passe en `PENDING_APPROVAL`
- tant qu’elle n’est pas approuvée, elle ne doit pas être considérée comme finalisée selon le cas
- historiser :
  - qui a demandé
  - qui a approuvé / rejeté
  - date
  - commentaire
- statuts minimum :
  - PENDING
  - APPROVED
  - REJECTED
  - CANCELLED

## DTO minimum
- ApprovalRuleDto
- CreateApprovalRuleDto
- UpdateApprovalRuleDto
- ApprovalRequestListItemDto
- ApprovalRequestDetailDto
- ApproveRequestDto
- RejectRequestDto

## Validators minimum
- CreateApprovalRuleDtoValidator
- ApproveRequestDtoValidator
- RejectRequestDtoValidator

## Services attendus
- IApprovalRuleService / ApprovalRuleService
- IApprovalService / ApprovalService

## API attendue
### Approval rules
- GET /api/approval-rules
- POST /api/approval-rules
- PUT /api/approval-rules/{id}
- PATCH /api/approval-rules/{id}/status si utile

### Approval requests
- GET /api/approval-requests
- GET /api/approval-requests/{id}
- POST /api/approval-requests/{id}/approve
- POST /api/approval-requests/{id}/reject

# 8) MODULE — GESTION DÉTAILLÉE DES ÉCARTS

## Objectif
Quand une session est fermée avec un écart, je veux une gestion plus riche qu’un simple champ `VarianceAmount`.

## Entités à prévoir
- VarianceCase
- VarianceAction
- VarianceJustification

## Cas à couvrir
- écart positif / négatif
- justification obligatoire au-delà d’un seuil
- validation superviseur au-delà d’un seuil
- suivi des actions correctives

## Règles métier
- si ABS(VarianceAmount) > seuil justification => justification obligatoire
- si ABS(VarianceAmount) > seuil validation => approval request
- possibilité d’ouvrir un dossier d’écart lié à la session

## DTO minimum
- VarianceCaseDto
- CreateVarianceJustificationDto
- VarianceActionDto

## Validators
- CreateVarianceJustificationDtoValidator

## Service
- IVarianceService / VarianceService

## API
- GET /api/variances
- GET /api/variances/{id}
- POST /api/variances/{id}/justify
- ajoute d’autres endpoints si nécessaire, mais reste pragmatique
